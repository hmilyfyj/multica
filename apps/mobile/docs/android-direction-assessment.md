# Android 客户端后续方向评估

评估日期：2026-09-22；对应任务：FEATURE-639。本文是路线建议，尚未改变项目排期。

建议现在以手机网页版为主，优先尝试添加到主屏幕；Android RN 客户端保留源码、签名和发布记录，转为维护状态，暂停以“追齐整个网页版”为目标的扩张。只有出现明确、经常使用且网页不能满足的系统能力需求，才继续投入专项开发。

已经完成 Android 适配，并不意味着后续投入必须继续。当前更值得投入的是用户每天实际使用的入口。也没有必要立刻删除 RN 工程，放弃可复用的构建、交互和发布成果。

## 判断依据与边界

本轮核对了 `hmilyfyj/multica` 的 `main@403011e6dc31cfb3a8023b069f5f3c11566d168b`、最新 GitHub Release、FEATURE-553 总览、FEATURE-541 相关评论，以及 580 / 582 / 583 / 589 的当前任务记录。

最新公开 APK 是 [Android 0.1.2 / vc14](https://github.com/hmilyfyj/multica/releases/tag/android-v0.1.2)，源码为 `4808866f1fbe6aa94469ea08c5a721874ef91871`。该版本到此次 main 之间，`apps/mobile` 与 `apps/web` 没有文件差异。用户手机上实际安装的版本、线上网页的部署版本尚未核实。

本轮是源码与历史证据评估，没有重新启动模拟器、操作真机或对线上网页做性能测试。用户反馈“网页版明显更流畅”是当前选择日常入口的有效依据；具体性能根因仍需测量。

### 1. 功能差距有持续维护成本

[仓库共享边界](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/AGENTS.md)和 [mobile 约定](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/mobile/AGENTS.md)明确：web / desktop 共享 `packages/views`；mobile 独立维护 UI、状态、API、缓存、实时订阅和发布，只共享类型、纯工具及可跨平台的 schema。

因此，“iOS 工程打开 Android 平台，业务代码大部分可复用”成立；“网页版新增功能会自动进入 Android”不成立。继续全面对齐，意味着持续承担第二套客户端的功能实现、行为一致性和回归成本。部分缺口属于整个移动客户端，并非 Android 平台适配遗漏。

当前情况也不宜继续沿用早期的缺失清单：

| 能力 | 本次核对结果 | 对方向选择的含义 |
| --- | --- | --- |
| 子任务、收件箱筛选与归档、关联 PR、聊天停止与重命名、run 详情 | 已进入 0.1.2 对应源码 | 已完成相当多补齐，但不能据此宣布真机体验达标 |
| 评论引用（580）、聊天项目上下文（582）、宽表格修复（589） | 当前任务均为 `todo`，未进入当前 main | 总览中“在跑”是旧进度，尚不能算交付 |
| 待发队列管理（583） | `backlog` | 仍需单独实现 |
| Agents / Autopilots 等管理能力 | 已有移动查看入口，部分以只读为主 | “有这个页面”与“能完成网页上的全部操作”不同 |

FEATURE-541 中 2026-09-19 的两轮功能盘点与本次任务记录可交叉核对。需要继续 RN 时，应按“查看任务 → 读完整结果 → 回复 → 停止运行”这种完整流程选范围，避免逐页追平。

### 2. 流畅度还没有可靠的达标证据

[Android 平台规范的性能记录](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/.trellis/spec/mobile/frontend/android-platform.md#markdown-渲染与代码高亮feature-550-实测基线-commit-7520b1bc6)明确：同一模拟器 Debug 协议的卡顿帧比例曾为 2.39% / 28.17% / 33.33%，受宿主负载明显影响，不能作为帧率验收结论，真机 Release 性能留待后续。已有模拟器冒烟和部分真机通知排查也不能代替核心流程的真机性能回归。

不能直接归因为“RN 天生慢”，也不能承诺换库或重写就会好。源码已在 [任务时间线](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/mobile/components/issue/timeline-list.tsx)和 [聊天列表](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/mobile/components/chat/chat-message-list.tsx)使用 FlashList v2；“换成虚拟列表”不是新的解决方案。

若做诊断，优先测长线程、流式更新、Markdown / 代码高亮引起的布局与渲染开销，再区分网络请求、缓存失效和主线程阻塞。[Markdown 入口](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/mobile/lib/markdown/markdown.tsx)在内容变化时重新预处理、分块，正文与代码又使用不同原生组件，这提供了排查位置，但还不是已证实的卡顿原因。

宽表格则是已知可用性问题：[渲染 ADR](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/mobile/docs/markdown-rendering-adr.md)记录了原生渲染的复杂内容边界，用户也已报障。对以阅读智能体结果为主的产品，内容能完整阅读应优先于再补一个管理页面。

### 3. 网页已经具备主屏幕入口基础

[web manifest](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/web/app/manifest.ts)已有图标、`display: standalone`、`start_url: /inbox` 和快捷入口；[布局配置](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/apps/web/app/layout.tsx)也有主屏幕相关 metadata。因此可以先用手机浏览器菜单里的“安装应用”或“添加到主屏幕”，具体名称和独立窗口行为取决于浏览器及线上部署。

这只是复用现有网页的安装入口。源码检索在 web / core / views 中没有发现 Service Worker 注册或 PushManager 接入；本轮不能宣称网页已支持离线工作或后台 Web Push。安装入口、离线能力、后台推送是三项不同能力。

### 4. 当前 RN 通知也没有构成可靠的后台优势

[本机通知与后台取证记录](https://github.com/hmilyfyj/multica/blob/403011e6dc31cfb3a8023b069f5f3c11566d168b/.trellis/spec/mobile/frontend/android-platform.md#本机通知方案-afeature-562基线-commit-3fd34cc21)说明：通知依赖 App 收到 WebSocket 事件后本机投递，没有独立推送通道。进程被冻结或回收时，不能保证及时收到；澎湃 OS 上已有相关真机取证。

如果真正需要的是“锁屏或进程退出后也及时提醒”，应单独评估目标手机的厂商推送、具备 GMS 环境时的 FCM，以及后端发送链路；网页 Web Push 也要验证浏览器、网络和 ROM 支持。不能把继续做 RN 或把网页装成图标，等同于解决通知。前台服务会引入常驻通知和后台运行约束，也不是默认答案。

## 路线比较

| 路线 | 收益 | 持续成本与限制 | 建议 |
| --- | --- | --- | --- |
| 移动网页为主，使用主屏幕入口 | 直接使用已有功能；主要维护一套 web 业务 UI；更新由服务端部署提供 | 窄屏、键盘、附件、登录恢复仍需验证；系统集成受浏览器约束 | 当前首选 |
| 持续完善 RN | 可定制原生交互、系统集成；保留已有 Android 工程成果 | 独立功能实现、缓存与实时一致性、Android 回归和 APK 分发长期存在 | 仅对明确的移动核心流程与系统需求投入 |
| 网页容器：TWA 或 WebView / Capacitor | 复用网页内容，同时提供 APK 入口或原生桥接 | TWA 需域名关联及浏览器支持；WebView 需处理登录、返回、键盘、上传下载、外链与桥接 | 先证明必须有 APK 或原生桥接，再考虑 |

只有桌面图标需求时，先验证现有网页安装入口。若必须分发 APK 且主要展示固定站点，可优先做 TWA 可行性验证；若确实需要原生 API 桥接，再考虑 WebView / Capacitor。容器并不自动增加业务功能、提升流畅度或解决后台推送。

## 建议的下一步

1. **日常使用转向当前体验更好的网页。** 在常用安卓手机上尝试主屏幕入口，检查登录保持、返回键、键盘、宽表格、附件上传下载和评论落点。以这条入口作为后续体验基线。
2. **建议停止新增 RN 全量追平排期。** 保留仓库、现有 APK、签名材料及构建说明；仍有人使用时处理崩溃、数据正确性、安全及后端兼容问题。580 / 582 / 583 / 589 等已有任务需要由项目负责人结合新方向重新排序，本评估没有取消或启动它们。
3. **后续开发优先改善手机网页的实际障碍。** 当前没有必要另做一套“移动网页重写”；先修现有响应式页面中影响完整流程的问题。通知作为独立需求评估。
4. **只有 RN 有明确价值时，给一次有限的修复机会。** 建议预算上限为 3–5 个工程日，包含定位、少量针对性修复和一次集中真机对比；这是止损预算建议，不是交付估时。若只需现在已有的网页功能，可以跳过这轮投入。

## 如果保留 RN 主动开发：继续与停止的条件

下面是建议验收门槛，并非本次测得的结果，也尚未成为项目强制规范。

对比应使用用户常用的同一台真机、同一网络和后端、同一数据规模，记录机型 / Android / ROM / 浏览器 / APK 版本。RN 使用生产 Release，网页使用生产构建。冷启动与热打开分开统计，避免用 Debug 包或模拟器对比手机浏览器。

| 观察项 | 建议取证与门槛 |
| --- | --- |
| 高频完整流程 | 收件箱进入指定回复、长线程阅读并回复、聊天查看输出并停止任务，均能完成；无内容裁切、丢输入或跳错落点 |
| 打开与响应 | 冷 / 热场景分别至少 20 次，记录中位数与 P95；RN 核心页 P95 打开耗时不超过网页的 1.2 倍，本地点击反馈 P95 低于 100ms |
| 长列表 / 流式输出 | 固定样本、固定刷新率，每端至少 3 段 30 秒录屏和帧时间取证；以同口径的系统帧时间比较，卡顿帧比例目标低于 5%，不出现超过 200ms 的可见停顿 |
| 成本 | 3–5 个工程日内能定位主要瓶颈并完成有限修复；若发现需整体重做数据层或渲染体系，返回路线评审，不无限追加预算 |
| 原生价值 | 至少一项用户经常使用、网页无法满足的能力经真机验证；若选择后台通知，要单独记录锁屏、切网、进程回收和目标 ROM 的实际可达性 |

当核心体验接近网页、原生价值确实存在且维护成本可承担时，继续做范围有限的 RN 客户端。若完成这轮仍明显更慢，或并没有独有的高频价值，就保持网页优先、RN 维护状态。即使性能达到网页水平，也不自动构成全面追平网页功能的理由。

长期停止主动开发后，可以另行决定是否正式归档 Android；保留发布与签名记录即可，无须为了“止损”先删除工程。
